# TTS 合成速度与效果测试

在 GPT-SoVITS 实际运行的机器上执行。脚本只合成文件，不发送 QQ 消息。
DS已回传旧提交 `494449c5` 的真实合成反馈，摘要见 [改进日志](TTS-IMPROVEMENT-LOG.md)。
本轮修复仍需在模型机器复测；云端离线回归或固定响应数据不能代替真实合成成绩。

## 一条命令运行

项目引擎与参考音频已按配置安装时，在仓库根目录执行：

```bash
npm run bench:tts -- --runs 3 --concurrency 3
```

如果实际用的是另一目录里的适配器，可指定它的路径：

```bash
node scripts/benchmark-tts.mjs --engine "<实际使用的 tts-core.cjs 完整路径>"
```

脚本只依赖 Node.js 内置模块，也可以单独复制 `benchmark-tts.mjs` 到模型机器上，
再用 `node benchmark-tts.mjs --engine "<适配器完整路径>"` 执行。
默认使用该适配器的 `DEFAULT_REF`。临时换参考音频和原文时：

```bash
node scripts/benchmark-tts.mjs --engine "<适配器完整路径>" --ref-audio "<参考.wav>" --prompt-text-file "<对应原文.txt>"
```

原文必需且应逐字对应参考音频。语言默认均为中文；DS反馈中的参考原文是日语，
应追加 `--prompt-lang ja --text-lang zh`，并把桥接的 `voice.tts.promptLang` 配为 `ja`。
这是明确记录语言条件，不代表已验证听感改善。不同语言配置的两轮报告不能直接作为速度A/B对照。

默认完成 16 次真实合成：首次短句 1 次，4 类语料各 3 轮，再同时提交 3 条短句。
每次运行写入 `tts-benchmark-results/run-*/`，包含 `report.md`、`report.json` 和试听 WAV。
可用 `--out-dir` 指定输出根目录，旧结果不会被覆盖。
预先运行的外部服务不会被本项目适配器停止；此次脚本自行启动的服务会在结束时清理。
合成或音频检查失败会计入失败次数；依赖缺失则生成 `blocked` 报告，不生成虚构测量值。

## 怎么看速度

- `wallMs`：从调用 `synthesize()` 到完整 WAV 落盘，包含排队、启动、探活和文件写入。
- `adapterMs`：适配器返回的 `ms`，本项目实现只包含 HTTP 合成与落盘，不含排队或启动。
- `timings`：新版额外返回 `queueMs`、`serverMs`、`requestMs`、`saveMs`、`slotMs` 和 `totalMs`。
  JSON保存逐条值及P50/P95，Markdown显示分阶段明细；旧版没有这些字段时保留空值。
- `RTF`：`wallMs / 音频时长毫秒`。小于 1 表示生成速度快于音频播放速度。
- P50/P95：只统计成功样本，失败单独计数。默认样本数少，P95 只能用于观察。
- 并发阶段：分别观察每条请求耗时与失败；串行队列不会把三条请求变成一次并行推理。

排队超时默认90000ms，与引擎和自动回复一致。DS反馈中15000ms下三请求仅1条成功，
60000ms时3/3成功、总耗时21.9秒；90秒是保守留余量，尚需本轮复测。
慢设备下第三条可能等待前两条完成，可分别用 `--queue-timeout-ms 15000`、`60000`、`90000`
比较 `queueMs` / `slotMs` 的P95和失败率，再按能接受的等待调整实际桥接配置。
不同排队预算的结果应分别报告，不能用更长预算的成功率代替旧默认的失败率。
`serverMs`含启动或探活，`requestMs`含HTTP传输；不要把 `wallMs - adapterMs` 全部标为排队。

基准直接调用引擎，保留107字符长句用于压力观察；不受自动回复80字符门槛限制。
报告记录目标/参考语言。90秒队列、300秒启动和80字符只是当前预算选择，没有改变模型吞吐。

`first` 只是该次脚本的首次调用。报告会标记端口预先是否已有HTTP响应，**不能仅凭首次调用就称为冷启动**。
裸 `GET /tts` 返回500仍会标记已响应；这不保证合法POST推理成功，也不应因此启动第二套服务。
300秒启动预算尚未做实机冷启动验证。要测真正冷启动，请在方便时手动退出专用于测试的服务再运行脚本；
内存不足时标记BLOCKED，不额外启动模型实例。
脚本不会自动关闭外部服务来制造冷启动。

## 怎么看效果

脚本检查 RIFF/WAVE 结构、采样率、声道、时长、峰值/RMS、接近满幅样本比例、
静音比例及首尾/最长静音。静音按 20ms 窗 RMS 低于 -45dBFS 估计，可能把轻声当成静音。
“接近满幅”是削波风险提示，不能证明已经失真。

这些指标不能判断自然度、漏字、错读、复读或音色相似度。请按报告里的清单试听：

| 文本 | 重点 |
|---|---|
| short | 起音、尾音是否完整，语气是否自然 |
| medium | 数字、标点停顿是否正确 |
| long | 是否漏字、复读、异常停顿或音色漂移 |
| mixed | 日期、金额、英文缩写及中英切换 |

## 判断优化空间

1. 首次很慢、后续稳定：优先在桥接启动时调用 `warmup()`，把服务加载时间移出用户回复。
   当前 `warmup()` 只检查HTTP存活；模型首次推理是否仍慢需要通过第一条和后续同类语料比较。
2. 后续合成也慢：检查 GPU 使用、半精度和模型版本，再对官方 API 支持的
   `sample_steps`、`batch_size`、分句方式进行一次一项的 A/B 测试。需确认所装整合包支持这些字段，
   本项目当前适配器仍固定 `batch_size=1`，没有开放采样步数；仅在命令行传同名参数不会生效。
3. 只有并发慢或超时：这是排队压力。先缩短回复、提高真正的模型吞吐，必要时用独立模型实例分担；
   共用模型状态时，直接删除串行限制可能带来音色和参考状态串扰。
4. 只需要更快在 QQ 中听见：当前链路先收完整 WAV，再交给网关转码发送，
   单独开启模型流式响应不能直接缩短 QQ 语音条的完整发送时间，必须连同发送链路验证。
5. 音色不稳或错读：优先检查干净的 3~10 秒参考音频及逐字原文，再比较语言设置和切句方式。

两次对比用相同硬件、相同模型/音色/参考文本、相同服务状态，避免其它 GPU 任务。
用 `--label before` / `--label after` 区分报告，每次只改一个参数。
API 随机采样会带来差异，至少比较多轮速度和多段试听，不能用一个样本判定质量提升。

官方 API 参数参考：<https://github.com/RVC-Boss/GPT-SoVITS/blob/main/api_v2.py>。
这里列出的采样步数、批大小是待验证选项，尚无本机实测证明哪组更好。
