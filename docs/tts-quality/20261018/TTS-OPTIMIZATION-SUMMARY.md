## 2. 阶段 0：环境、调用链与参考素材核对

1. 记录 Node、Python/torch/CUDA、模型版本及权重标识、半精度状态、实际 API 地址、适配器和相关配置文件哈希。只收集必要字段，不导出完整环境变量、账号或令牌。
2. 从真实适配器定位请求字段和默认值；可只读获取服务的 `/openapi.json`，或查看本机 API 定义。不要把裸 `GET /tts` 的 HTTP 500 当成模型故障，也不要将接口接受字段等同于推理实现使用了字段。
3. 核对 `config → bridge 调用 → tts-core → API → 推理函数`。已有 bridge 的自动语音调用主要传参考、语言、超时等，没有读取采样步数/温度配置；不能只向 config 增加一个字段就宣称生效。
4. 列出常态、担心、开心的参考 WAV、对应原文、语言、时长、采样率、单声道/多声道、峰值与听感问题。本计划固定日语目标文本，选择实际确为日语的参考时使用 `textLang=ja`、`promptLang=ja`；原文必须对应音频，不把中文译文或情绪标签送进合成文本。若新来源是其他语言配音或歌曲，不强行标为日语，也不悄然修改生产语言。
5. 读取现有音量、归一化、重采样及 SILK 转码路径，记录是否存在多次有损转换；先不改变处理链。

可在确认路径后使用以下 PowerShell 命令记录基线：

```powershell
$bridgeRoot = '<your-bridge-root>'
$ttsEngine = '<your-tts-core>/tts-core.cjs'
$probeBinary = '<your-gpt-sovits>/ffprobe.exe'
node --version
```

复用现有模型服务，在空闲窗口串行测评，避免与实际聊天请求同时改变共用参考状态。适配器模块内的串行锁不等于跨进程锁。服务不可用、显存不足或无法隔离请求时，完成脚本和核对材料，标记 `BLOCKED`；不要为测评拉起第二套模型或停止其他服务。

## 3. 阶段 1：首批 12 条 WAV，先比较参考音频

### 3.1 固定三组参考

- `R0`：当前常态参考，作为基线，保持原文件不变。
- `R1`、`R2`：同一目标音色、同为常态风格的两组候选参考。优先选择 3～10 秒、单人、完整自然语句、无配乐和明显混响的录音，以本机版本的有效时长约束为准。
- 每组必须有逐字核对的日语原文。先试听参考本身，标记底噪、削波、气声、混响和断字；不默认叠加强降噪或音量拉升。若裁切或处理，另存派生文件并记录来源及处理参数。
- 不拿担心/开心参考与常态比较后直接宣称音质改善。已有情绪参考在后续各自同风格的对照中再评估。
- 如果没有两组有效候选，按实际组数执行并报告缺口；不要用复制文件或改文件名凑三组。

### 3.2 从用户提供的音源挑选片段

1. 优先核对本机已有同源文件；如从链接取得素材，记录实际视频标题、BVID、配音版本、发声语言与可识别的段落信息。链接不可访问时记录原因，继续已有参考的核对与工具准备，不编造素材内容。
2. 为每个候选记录 `source_bvid`、`start_seconds`、`end_seconds`、`speaker_or_version`、`spoken_language`、源文件与输出文件 SHA256，以及逐字原文。不能确定说话者或配音版本时明确标注，不把该候选当成已确认同声线。
3. 优先选择自然对白，避开其他角色插话、解说、重叠人声、配乐、明显音效、喊叫失真及歌曲。常态候选保持接近现用参考的情绪强度；担心/开心另行同类比较。
4. 保留源音轨，裁切片段另存 PCM WAV，避免反复有损编码；采样率和声道处理按本机模型实际要求进行并记录，不用盲目升采样代替音质改进。
5. 字幕只作转写起点，必须听音核对实际台词、漏字和重复句；中文翻译不能作为日语 `prompt_text`。保留完整起音/尾音及适度停顿，不为凑时长截掉词句。
6. 如果所有片段都有背景音乐，可将人声分离结果作为独立候选，保留原声对照，检查金属感、残留音乐和辅音损伤；本轮不强制分离、安装大模型或启动额外 GPU 模型。没有合格素材就报告候选不足。

### 3.4 评测工具要求

在独立目录编写 `quality-runner.mjs`，调用实际 `tts-core.cjs` 的 `synthesize(text, options)`，每次显式传参考路径、逐字原文和日语语言设置。保留现有采样、语速、切句方式及模型，唯一实验变量是参考组；参考原文随其音频配套改变。

- 先确认适配器实际支持的选项。需要增加日志时仅在副本或临时测试入口完成，记录真正发给 API 的合成字段；不要仅保存预期配置。
- 使用 UTF-8 文件保存语料与 JSON，由 Node 读取并 `JSON.stringify`。不要经 Windows shell 将非 ASCII 内容拼成 `curl -d` 参数；过去已出现乱码输入导致失败的样本。
- 不调用 QQ 发送入口，不为制造冷启动停止模型，不调用会关闭共享服务的 `engine.stop()`。
- 一次最多一个推理请求。每个语料在三组间轮换顺序，保存完整 `run-order.json`；不要总是先跑 R0 再连续跑全部候选。
- 如果 API 和推理实现确实支持 seed，为同一句固定相同 seed，记录实际 seed；否则明确随机性未受控。固定 seed 也不等于完全消除 GPU 非确定性。
- 首次状态单独记录。确需预热时最多增加 1 次，单独记为预热、不混入 12 条计数；不能将脚本第一次调用写成冷启动。
- 显式请求将输出写入本次独立目录；旧适配器忽略 `outDir` 时，将本次返回的文件复制归档并记录原路径，不删除共享缓存或其他任务文件。每条输出唯一文件名，保留原始 WAV。失败、超时、异常短音频和额外调用均写入记录，不悄悄重试并覆盖。
- 记录端到端耗时、适配器耗时、可获得的分阶段计时、音频时长、RTF、字节数、采样率/编码、峰值、静音和削波风险。旧适配器没有的字段保留 `null`，不能推算成已测值。
- 本轮端到端计时从调用 `synthesize` 开始，到完整 WAV 返回并确认可读为止；归档复制、波形分析与盲听副本处理另记，RTF 的分母为原始音频时长。所有组使用同一定义，不与旧报告不同测量范围的数值直接比较。
- 记录 GPU 显存观测值和采样间隔；使用定时采样时标注“采样期间最大值”，不能冒称精确峰值。不能观测则留空。

旧 `benchmark-tts.mjs` 默认合成中文，`--text-lang ja` 不会自动改写其语料，也不支持未实现的 `--sample-steps` 或自定义文本参数。可复用其 WAV 分析函数，在副本中实现本计划；不要直接运行默认 16 次测试代替本轮对照。

### 3.5 试听与初筛

创建盲听副本，隐藏 R0/R1/R2 标签，另存映射。原始文件保留；同一播放器和音量试听。响度差异干扰判断时可另存等响副本，记录处理参数，不能用处理后文件替换原始测量。

由能判断日语的试听者逐条记录：

| 项目 | 记录方式 |
| --- | --- |
| 发音与完整性 | 错读、漏字、复读、截断逐项标记位置；无问题也明确记录 |
| 自然度 | 1～5 分，5 为最自然，注明停顿/重音/句尾问题 |
| 音色一致性 | 对照目标角色/当前满意音色，1～5 分，5 为最一致 |
| 噪声与失真 | 底噪、金属感、爆音、辅音模糊、异常呼吸声及时间位置 |
| 偏好 | 候选更好 / 基线更好 / 持平 / 无法判断，并写一句理由 |

如果 DS 无法实际播放或没有人工评分，就交付盲听清单，结论写“客观检查完成，听感待确认”。不能用 ffprobe、RMS、文件更大、ASR 转写或主观猜测替代音质验收。

四句仅用于初筛，不计算具有稳定性含义的 P95，不宣称统计显著改善。候选至少不能增加明显漏字、复读、截断或音色偏移。暂以中位耗时增加不超过 20% 作为实时回复候选预算；这只是本计划的初筛门槛，超出者可列为较慢的品质候选，不能自动替换默认。

## 4. 阶段 2：有明确错读或停顿问题，再改文本处理

仅在阶段 1 已定位具体问题时开展；没有人工反馈时可以准备候选规则和工具，不宣布改善。

1. 为实际错读的人名、日期、金额或英文缩写制定小范围读法规则，保留展示原文，另存用于 TTS 的文本；不要对所有汉字或数字做粗暴替换。
2. 分别比较原标点与调整标点，或两个本机支持的切句方法；不要同一轮同时改读法和切句。
3. 保留 `日文||中文` 及情绪标签剥离机制，不将译文拼入语音，不截断句子来掩盖漏字或降低 RTF。
4. 选择 2 个已暴露问题的语料，基线与候选各合成 1 次，共 4 次。其余参考、seed、模型、采样设定保持相同。

输出规则前后文本、实际请求、4 次结果与差异补丁。只有错误得到复验改善、未出现新的读错时，才列为候选修复。

## 5. 阶段 3：参数核对与有界 A/B

参数能力表可以在前面独立完成；参数合成对照须在参考已选定或明确使用 R0 时进行，不混用不同参考。

| 待核对参数 | 核对重点 |
| --- | --- |
| `sample_steps` | 本机 v4 API 与推理路径是否支持、默认值和允许值；只比较现值与一个受支持的档位 |
| `temperature` / `top_k` / `top_p` | 实际默认、范围与是否参与当前推理；一次只改变一个 |
| `seed` | API 接收后是否传入实际随机采样；仅写到请求 JSON 不足以证明生效 |
| `speed_factor`、切句方式 | 记录现值；语速不作为本轮音质提升的默认手段，切句单独测试 |
| 超采样等选项 | 只有安装版本确实支持且资源允许时才列候选；提高输出采样率本身不证明细节改善 |

实现时优先改独立测试副本：配置定义、bridge 读取、适配器映射、API 字段与实际推理含义需要一致。新增参数要有类型、范围、默认兼容与未知字段处理；默认配置下请求语义保持原状。不要顺手替换现有部署专用适配器。

先选择最有依据的 1 个参数，2 个水平 × 2 个代表语料，共 4 次。参数取值依本机支持范围确定，不在未核对时硬填 32/64 等数值。出现超时、显存不足、短碎片、吞字等情况立即记录并结束该候选，不扩大并发、不用重启清掉失败记录。

参数越高不必然音质越好。报告同时列出听感、失败情况与耗时/显存代价；无明确收益就保留现值。若后续要继续搜索更多组合，先交付本轮结果与建议实验量，不自动展开网格搜索。

## 6. 阶段 4：QQ 转码与情绪方案的后续验证

### 已有文件可用时，本轮只做离线诊断

寻找上一轮有效 QQ 样本的源 WAV 与对应接收/转码文件，确认是同一条音频再比较。只有源 WAV 或没有对应关系时标记 `NOT_TESTED`，不能用不同句子、不同情绪的文件得出转码损伤结论。

若发现 WAV 良好、转码后明显变差，检查重复有损转换、重采样、过大增益与归一化；在独立副本试验单次转码或适度电平处理。不得将“文件变大”写成音质提升，也不默认开启重降噪。没有可用接收文件时不新增 QQ 发送。

### 后续可选工作，不纳入首批 12 条

- 对担心、开心参考分别做同情绪、同目标音色的对照。参考也影响韵律和感知音色，不能保证“只改情绪、语速和音色绝对不变”。
- 参考与文本/参数均无明显收益后，再提出训练素材清洗、标注修订、微调或更换模型/声码器的可行性报告。先评估 4GB 显存与时间成本，本轮不启动训练或下载大模型。
- 冷启动 0.32 秒异常和长尾延迟另做资源与模型日志诊断，不混入本轮音质对照，也不删除历史慢样本。

最终交付候选配置/差异补丁、修改范围、对现有行为的影响、针对性检查和可操作的恢复说明。保持静默/会话守卫、额度、内联音频、清理、译文发送结果和 WAV 校验，不把公共参考片段整体替换进私有 bridge。生产文件不自动应用。

4. 参数是否真正到达并被服务端使用？若无法确认，说明证据缺口。
5. 候选相对基线的耗时、RTF、失败与显存代价是多少？所有异常是否保留？
