# 用在你自己的声音上

这份配方不绑定任何特定角色或参考音频。下面是把它用到你自己 TTS 输出上的步骤，以及几个容易踩的坑。

## 1. 准备输入

- 让 TTS 输出 **48 kHz / 单声道 / PCM16** WAV；
- 必须使用**没有降噪过**的原始合成结果（重复降噪会吃掉辅音和气声）；
- 如果你是在一条已经处理过的音频上再试，先换一条新的。

## 2. 先只跑全局 NF43

```bash
python denoise.py my-tts.wav my-tts.nf43.wav
```

看输出的 JSON：

| 字段 | 怎么读 |
| --- | --- |
| `frames` | 必须与输入一致 |
| `lag_corrected` | 延迟补偿样点，正常应远小于 2400 |
| `gain_db` | 电平修正，绝对值应 ≤1 dB |
| `anchor_difference_db` | 处理后参考区间电平差，接近 0 才正常 |
| `clipped` | 必须为 0 |
| `compatibility.no_missing_selected_samples_filled` | 必须为 true，否则说明有样点被伪造 |

如果 `anchor_difference_db` 明显偏离 0、`clipped` 非 0，或者程序报“no foreground window”，说明这条音频不适合当前参数（例如整条都过轻或接近静音），先别继续。

## 3. 决定要不要 R4

R4 只在**你明确标出的时间窗**里动手。没有明确理由就别加——它也会动到齿音和辅音。

建议做法：

1. 在同一句上对比“合成原声”和“NF43 结果”，确认底噪问题是否已经解决；
2. 如果只有某一段还有高频毛刺/气声过强，再为那一段标一个窗口（≥120 ms）；
3. 一次先标一个窗口试听，不要一口气标十几个。

```bash
node r4/apply.mjs --in my-tts.nf43.wav --out my-tts.r4.wav \
  --regions '[{"start":3.2,"end":4.1,"highFloor":0.94}]'
```

要更强的高频衰减再对该窗口加 `"hf90": true`。`highFloor` 越接近 1，清理越轻。

## 4. 怎么听

固定文本、固定参考音频、固定 seed、固定推理参数、**固定播放音量**，用同一次请求的处理前后文件做 A/B。分别评价：

- 说话期间的底噪是否更轻；
- 辅音、齿音是否变闷或被吃掉；
- 气声是否还在自然范围；
- 整体音色、语速、自然度有没有变化。

不要用整体音量、频段能量比例或滤镜系数代替听感评分。RMS 匹配不是感知响度归一，高频能量下降也不等于真实 SNR 提升。

## 5. 常见错误

- **对已降噪文件再跑一次 NF43**：会过度处理，人声发薄。
- **把一次性区间写进默认配置**：不同句子长度不同，区间必须每条重标。
- **在编码成语音条之后再解码降噪**：有损编码会带来新的高频损伤，且顺序也错了。
- **把 0.90 当“气声减少 10%”**：它是幅度系数，实测高频能量约 −19%，是否可接受只能听。
- **用不同句子做 A/B**：文本不同就无法归因，必须同一次请求的前后文件。

## 6. 接到自己的工程里

按 `TTS 合成 → 尾部裁剪/补白 → 全局 NF43 → 可选 R4 → 音量/响度 → 编码发送` 的顺序接入。失败时保留上一阶段结果：

- NF43 失败 → 用原始合成音频；
- R4 失败 → 用 NF43 结果，并如实记录 `no-regions` 或错误原因；
- 不要因为 R4 失败就重跑 NF43。

示例见 [`packages/voice-out/quality/postprocess.cjs`](../packages/voice-out/quality/postprocess.cjs) 与同目录 `README.md`。
