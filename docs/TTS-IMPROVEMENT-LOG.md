# TTS 改进日志

日期：2026-10-17（UTC）。目标仓库：<https://github.com/Kut1nashi/dsh-qq-onvoice-chat>。

本次工作包含 TTS 稳定性修复、测速工具、测试与交付说明。
没有安装或提交模型、音频库、参考音频、Python 运行时、账号凭据或本机配置。

## 问题与修改

| 原问题 | 修改后的行为 | 主要文件 |
|---|---|---|
| 任意 HTTP 响应都被当成服务就绪 | 仅接受成功响应或 400/422 校验响应，释放响应体 | `engines/tts-core.cjs` |
| 子进程启动异常没有完整处理 | 将启动错误、退出、信号、超时转换为可捕获异常并清理进程 | `engines/tts-core.cjs` |
| 启动与停止缺少协调 | 并发启动共用任务；停止取消启动与排队；只结束本模块启动的服务 | `engines/tts-core.cjs` |
| 服务异常时可能重复拉起并遗失原进程 | 运行中进程探活失败时保留句柄并报错 | `engines/tts-core.cjs` |
| 文本进入长 URL，多请求同时访问共用模型 | POST JSON；单实例串行推理，最多排队8条 | `engines/tts-core.cjs` |
| 只检查返回内容非空，响应内存无上限 | 有界流读取、RIFF/WAVE 文件头校验、UUID 文件名和失败写盘清理 | `engines/tts-core.cjs` |
| ffmpeg 报错后残留计时器或返回旧切片 | 释放计时器、限制错误日志长度、检查退出码和空产物 | `engines/tts-core.cjs` |
| 自动回复文件长期累积 | 无论发送成功或失败，均清理本次合成产物 | `bridge/voice-out.tts.js` |
| 合成期间状态改变仍继续发送 | 合成后重查静默、启用开关和额度；异常退回文本 | `bridge/voice-out.tts.js` |
| 缺少可重复的本机性能与波形检查 | 标准语料、首次/后续/并发测量、WAV 指标、试听文件及报告 | `scripts/benchmark-tts.mjs` |

上表中的引擎路径相对于 `packages/voice-out/`。
发送内核仍使用原有语音库边界、审计与回读校验机制。
`bridge/` 是接线参考片段，需要按 [接线说明](INTEGRATION.md) 合并到实际桥接仓库。

## 配置与兼容性

- `queueTimeoutMs`：排队预算；引擎默认同 `timeoutMs`，自动回复默认 15000。
- `startTimeoutMs`：服务探活与启动预算，默认 180000。
- `timeoutMs`：HTTP 推理及响应体读取预算，默认 120000。
- `maxBytes`：引擎默认 20 MiB，自动回复使用 `voice.maxBytes`。
- 整合包目录：`VOICE_TTS_GSV_DIR` → 引擎旁 `gsv-dir.txt` 首行 → `./GPT-SoVITS`。
- 可用 `VOICE_TTS_PYTHON`、`VOICE_TTS_FFMPEG` 指定可执行文件完整路径。

各阶段独立计时，总等待时间可能为三个预算之和。
每次合成返回独立文件，调用方负责释放；自动回复会自动清理，测速会保留试听副本。
串行保护仅覆盖同一进程内同一模块实例，不是跨进程或跨客户端的模型锁。

## 适配器固定响应对照

测试使用进程内 `Response` 与5秒、320044字节波形，包含写盘，**没有 HTTP 网络或模型推理**。
CPU：AMD EPYC 9V74 80-Core Processor；Node.js v24.19.0。
每版先运行8次，再测立即响应50次及固定100ms响应15次。
先测原版后测修改版，存在执行顺序与缓存偏差；仅用于观察代码开销量级。

| 项目 | 原版 | 本次修改 |
|---|---:|---:|
| 立即响应 P50 | 0.584ms | 0.739ms |
| 立即响应 P95 | 0.751ms | 1.018ms |
| 固定100ms响应 P50 | 101.311ms | 101.326ms |
| 三请求分别完成耗时 | 101.669 / 102.410 / 103.052ms | 101.590 / 202.863 / 303.880ms |
| 最大同时请求数 | 3 | 1 |

结论：该负载下新增校验与异步写盘的开销很小；没有证据证明模型推理变快。
串行队列会增加后续请求等待，这是保护共用推理状态的代价，需要在本机评估超时率。

### 排队预算与配置

- 发现参考 `voiceCfg()` 未返回 `.tts`，已补透传；模块路径和自定义排队预算现在可沿调用链生效。
- `synthesize()`增加单调时钟分段计时，分开记录排队、探活/启动、HTTP、落盘和合成槽占用。
  基准JSON汇总P50/P95，Markdown展示明细，旧引擎缺字段时保留未知。
- 保留15秒默认响应预算。CPU上三请求可能积压，30–45秒仅作为本机对照候选，
  需按实际P95、并发数和文本降级率决定，尚未获得真实模型数据。

### 文件清理与发送

- 参考发送函数只等待网关HTTP响应。为消除对部署版本异步读路径时机的依赖，
  TTS现在在发送槽内生成有界内联音频快照，发送 `record.data.file = base64://...`。
  原始WAV和音量产物删除后，后续网关处理仍持有完整字节；失败时也不再依赖这些路径。
- AI输入解析仍只允许库内本地文件，审计、大小限制、额度和发送守卫保留；
  内联编码仅在可信发送链内部进行。Base64使传输体积约增加三分之一，实际网关请求体限制和延迟仍需验证。
- 新TTS片段合成前检查发送端内联能力；旧发送函数没有能力声明时安全降级文本，
  避免其忽略新参数后继续以路径发送。
- 用户已确认部署发行包为 `@snowluma/runtime v1.14.20`；已核对该标签的
  [发行清单](https://github.com/SnowLuma/SnowLuma/blob/v1.14.20/packages/runtime/package.json)、
  [语音加载实现](https://github.com/SnowLuma/SnowLuma/blob/v1.14.20/packages/protocol/src/highway/ptt-upload.ts#L100)
  及 [base64源读取](https://github.com/SnowLuma/SnowLuma/blob/v1.14.20/packages/protocol/src/highway/utils.ts#L68)，确认该版本源码支持内联语音。
  [OneBot返回链路](https://github.com/SnowLuma/SnowLuma/blob/v1.14.20/packages/onebot/src/actions/message.ts#L122)
  和 [媒体构建](https://github.com/SnowLuma/SnowLuma/blob/v1.14.20/packages/core/src/bridge/apis/message.ts#L373)
  使用await，正常成功响应前会执行媒体处理；截图提出的0字节问题尚未被实测证实。
  内联快照同时减少HTTP超时/失败后清理路径的时序依赖。
  本次完成的是版本源码核对，实际发行二进制、用户bridge.js及QQ端到端仍需验证。
